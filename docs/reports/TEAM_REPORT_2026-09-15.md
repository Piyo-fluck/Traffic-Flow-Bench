## 4. L の中身

### 4.1 Task 1：CNN ＋月ごとの補正＋テスト時学習

- **CNN 本体は E と同じ**（膨張畳み込みの残差ブロック12個、幅64×2本＋幅128×1本の平均。詳細は前回レポート）。
- **月ごとの補正**：入力の基準にしている「曜日×時間帯の平均（train）」に、その月の見えている値とのずれを足す。
  - ずれは平日と週末に分けて求め、データ量に応じて弱める（速度 κ=2日、流量 κ=10日）。
- **テスト時学習（新規）**：採点月（validation、private それぞれ）の見えているセルを使って、各 CNN を少しだけ追加学習する。
  - 見えているセルを毎回10〜50%ランダムに隠し、それを復元する自己教師あり学習（正解ラベルは使わない）。
  - 400ステップ、学習率 2e-4。月ごとに GPU で約2分。
  - 月内の疑似評価（見えているセルの20%を隠して採点、その20%は追加学習にも使わない）で、S_state 0.9494 → 0.9513、S_LWR 0.7702 → 0.7735。
  - Task 1 はオフライン課題で月全体を使ってよいので、ルール上の問題はない。

### 4.2 Task 2 onset：事前分布ドロップアウト＋IoU 期待値最大化

**モデル**
- 特徴量は E と同じ（履歴の速度・流量・密度の比、近隣リンクの値、渋滞しやすさの確率など）。
- **事前分布ドロップアウト**：学習時、窓ごとに確率50%で「渋滞しやすさ・始まりやすさの確率」の特徴をすべて0にする。
  - validation・private は train と別のシミュレーション実行で、渋滞の場所が入れ替わっている（前回レポート 5.1）。確率を丸ごと信じるモデルは外れる。
  - ドロップアウトで「確率をどこまで信じるか」を学ばせると、両月とも改善した。
- ドロップアウトの抽選と乱数の種を変えた5本を学習し、確率を平均する。

**判定（新規）：IoU 期待値最大化**
- 採点は集合の IoU なので、ベイズ最適な予測は「確率の高い順に k 個」で、k は IoU の期待値が最大になるように窓ごとに決める。F値・Jaccard の最適化として知られる定石。
- 具体的には、T+30 の各リンクの確率を高い順に並べ、`S_k / (k + P − S_k)` が最大になる k を選ぶ。
  - S_k：上位 k 個の確率の和。P：全リンクの確率の和。
  - 確率に倍率はかけない（c=1.0。採点月のデータで調整していない）。
- 以前の「確率の合計×1.2 を丸めた数」は、確率が薄く広がった窓で選びすぎていた。
- 同じ判定を ongoing に使うと悪化した。セル同士が時空間で強く連動していて、この計算の前提（セルごとに独立）が崩れるため。ongoing は従来どおり。

### 4.3 Task 2 ongoing：事前分布なし＋需要÷容量の特徴

- 渋滞しやすさの確率の特徴は使わない（すべて0）。新しい実行では、無い方が良かった。
- **需要÷容量の特徴（新規）**
  - 今日の需要水準：直近3スロットの流量を、train の「曜日×時間帯の流量の平均」で割った比。リンク単位の値と路線全体の中央値を半々で混ぜる。
  - その比に T+5〜T+30 の時刻の平均流量を掛け、容量で割った値。
  - その値の、下流4リンクの中の最大値。
  - T+30 と T−5 の平均流量の比（需要がまだ増えているか）。
- 確率0.65以上を渋滞とする。

- Task 3 は Task 1 の予測から自動で計算される。Task 1 の改善が少し波及する。
- Task 4 は E と同じ（ほぼ満点）。

## 5. 評価方法の見直し（今回いちばん重要な学び）

### 5.1 以前の疑似評価は、公式の onset 窓を再現していなかった

公式の窓の作り方を、配布物（`config/synthetic_release_v1.json` と window_index）から改めて確認した。

| | onset | ongoing |
|---|---|---|
| 本数 | 各パネル・各月5本 | 各パネル・各月5本 |
| 中身 | **その日最初の朝の渋滞**。履歴に渋滞がなく、T+30 で初めて現れる | 履歴に渋滞があり、先30分にも渋滞がある |
| 時刻 | 起点が4〜14時台 | 起点が7〜21時台 |
| 日付 | 97.5%が1〜7日目（実際には1〜5日目に並ぶ） | 83%が1〜7日目 |
| その他 | 起点どうしは6時間以上離す | 持続予測の IoU が0.9以下の窓だけ。履歴の観測率0.7以上 |

- 以前の疑似評価は、一日中の onset を拾っていたため、onset を過小評価し（0.3〜0.4 程度）、手法の差も薄めていた。
- 「その日最初の朝の渋滞」に絞った疑似評価（公式に近い疑似評価）に切り替えた。

### 5.2 落とし穴：公式の窓で消されている区間

- 公式の窓の予測区間とその後1時間は、Task 1 のデータから路線全体で消されている。
- 公式の onset 窓がある日は、その日最初の渋滞が消されているので、疑似評価は消去の直後にある不自然な「渋滞の始まり」を拾っていた。これが疑似 onset の27〜30%で、**履歴がほぼ空**だった。
- 公式の窓がある日と、消去と重なる窓を除外して評価し直した。

### 5.3 結果

- E の Task 2 を、公式に近い疑似評価で S_queue 0.63〜0.67 と評価した。LB からの逆算（約0.635）に近い。
- L の見込みは 0.864（幅 0.853〜0.870）で、実際は 0.86893。
- **教訓：Task 2 は「公式の窓の選び方」をまねた評価でないと、手法の良し悪しを見誤る。**

## 6. やって伸びなかったこと（今回分）

| 試したこと | 結果 |
|---|---|
| 物理モデル（CTM）で先30分を計算して渋滞を予測 | 公開されている容量パラメータが生成器の実際の挙動と合わず、IoU 0.10以下 |
| 道路の構造（車線減少・合流）とボトルネック容量に対する余裕度を特徴量に | onset に一貫した改善なし |
| リンクを識別できる特徴（位置・パネル番号）を外す | 両月で悪化（外すべきではない） |
| 同じ月の当日以外の日から作った渋滞地図（測定のみ） | onset がむしろ悪化 |
| 前日までの朝の渋滞位置を加える | 公式 onset 窓は1〜5日目で、それより前の日の該当箇所は消されているため本番では使えない |
| onset の細かい調整16通り（非採点セルの履歴利用、朝の窓だけで学習、判定の係数） | 一貫した改善なし（差はばらつきの範囲） |
| ongoing に IoU 期待値最大化を使う | 悪化 |
| 学習ラベルのノイズ対策（公式の正解はノイズなしの状態から作られる） | 影響は IoU で1.5%未満 |
| Task 3 向けの密度の工夫（密度を直接出す、補間した密度に合わせる） | 補間は悪化。そもそも伸びしろがほぼない（下記） |

**Task 3 の結論（証明済み）**
- S_LWR は「観測値の5分ごとの変化」を再現できたかを見る。観測値にはノイズが乗っている（密度で約3%）。速度と流量のノイズは互いに独立（相関0.0004）。
- ノイズのない真の状態を完璧に当てた「理想の予測」をシミュレーションすると、S_LWR の上限は約0.64〜0.68。今の CNN は0.649で、ほぼ上限。
- 残りは全体で最大 +0.004。README の「完璧な回答で S_physics 0.96」は、ノイズまで当てた場合の値で、どの参加者も届かない。

**副産物として分かった事実**
- ボトルネックで渋滞が捌ける流量（容量）は、別の実行どうしでも0.5%以内で一致する（道路の性質）。変わるのは需要で、どのボトルネックが渋滞するかは1%未満の需要差で決まる。

## 8. データ利用のルール（チームで統一。前回から変更なし）

- **Task 2 で使ってよいもの**
  - 各窓の履歴（T−60〜T−5）
  - train から学習したもの
  - 採点月のうち、窓の日付より**前の日**の公開データ
- **Task 2 で使ってはいけないもの**
  - 起点の時刻 T の観測（そもそも配布されていない）
  - 予測区間中のデータ、予測区間の60分後以降の本線データ
  - 予測区間中のランプ流量
  - 同じ日の起点より後、および後の日のデータ（「当日以外の同じ月」の効果は測定だけ行い、onset が悪化したので不採用）
- **Task 1・3・4** は期間全体を使ってよい（オフライン課題）。月ごとの補正とテスト時学習はこれに当たる。

## 9. 再現方法

**環境**：前回と同じ（Windows 11、Python 3.12、RTX 4090、メモリ16GB、`.venv`）。データは `data/kaggle_public/`（9/11 に作り直された版）。

**手順**（プロジェクト直下で実行）

1. 前提のファイルを作る
   - `powershell -File scripts\run_official_baselines.ps1`（Task 4 のファイル）
   - `powershell -File scripts\run_submission_E.ps1`（CNN 3本のチェックポイント）
   - `powershell -File scripts\run_submission_F.ps1`（F1 = E ＋ Task 1 の月ごとの補正）
2. Task 2 の onset 用（H）
   - `.\.venv\Scripts\python.exe scripts\t2_m1_predict.py --onset-prior dropout --ongoing-prior zero --onset-bags 5 --rounds-on 600 --rounds-og 3300 --alpha 1.2 --tau 0.65 --out-dir work\sub_t2robust_bag5`
3. Task 2 の ongoing 用（I）
   - 上と同じコマンドに `--stress` を付け、出力先を `work\sub_t2robust_bag5_stress` にする。
4. onset の行は H、ongoing の行は I から取って結合し、`work\sub_t2J\queue_{validation,private}.csv` を作る。
   - 窓の種類は `task2/<パネル>/<月>/window_index.csv` の condition 列で判定する。短い Python で実施しており、スクリプト化はしていない。
5. onset を IoU 期待値最大化で判定し直し、F1 に組み込む（K）
   - `.\.venv\Scripts\python.exe scripts\t2_redecide_onset.py --probs-dir work\sub_t2robust_bag5 --base-dir work\sub_t2J --rule ratio --c 1.0 --out-dir work\sub_t2K`
   - `.\.venv\Scripts\python.exe scripts\swap_task_rows.py --base work\sub_F1_ens3month_t2m1_t4ref\submission.csv --task queue --files work\sub_t2K\queue_validation.csv work\sub_t2K\queue_private.csv --out work\sub_K_ens3month_t2K_t4ref\submission.csv`
6. Task 1 のテスト時学習を入れて L を作る
   - `powershell -File scripts\run_submission_L.ps1`
   - 月ごとの追加学習、10パネルの推論、state の差し替え、K との差分チェックまでを行う。合計で約10分。
   - 出力：`work\sub_L_ttt_t2K_t4ref\submission.csv`（367MB）

**今回の主なコード**

| ファイル | 役割 |
|---|---|
| `scripts/t2_m1_predict.py` | Task 2 の本番予測（`--onset-prior dropout`、`--onset-bags`、`--stress` を追加） |
| `analysis/t2_demand_stress.py` | 需要÷容量の特徴 |
| `analysis/t2_expected_iou.py` / `scripts/t2_redecide_onset.py` | IoU 期待値最大化の評価と、本番の判定のやり直し |
| `analysis/t2_official_like_eval.py` / `analysis/t2_first_onset_eval.py` | 公式に近い疑似評価（消去区間の除外を含む） |
| `analysis/t1_ttt.py` / `scripts/t1_ttt_train.py` | Task 1 のテスト時学習（評価用と本番用） |
| `scripts/run_submission_L.ps1` | L の組み立て |

**注意（Windows）**：負荷が高いときに python.exe が異常終了することがある（ntdll の `0xc000070a`）。もう一度実行すれば通る。各スクリプトにやり直しの処理を入れてある。
