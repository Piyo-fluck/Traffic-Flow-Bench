# TrafficFlowBench：ベスト更新（Public LB 0.87687）の手法と、局所評価の較正

作成日：2026-09-16。対象コンペ：Kaggle「2026 IEEE Big Data - Traffic Flow Bench」。
同日の前レポート（ベスト 0.87505、提出 M）の続きです。

---

## 1. 結論（先に要点）

- **現在のベストは Public LB 0.87687（提出 R）**。M（0.87505）から **+0.0018**。
- 変えたのは **Task 2 の ongoing（渋滞継続中の窓）だけ**。onset・Task 1・Task 3・Task 4 は M と1行も違いません。提出物 698万行のうち変更は **715行のみ**で、すべて ongoing 窓です。
- 効いたのは新しい特徴量でも新しいモデルでもなく、**モデルの多様性**でした。ongoing の予測を
  「LightGBM 1本 + CNN 3本」から「**Transformer 4本 + CNN 3本 + 別設定の LightGBM 1本**」の重み付き平均に変え、しきい値を 0.60 → 0.45 に下げただけです。
- **重要な副産物：局所評価は約2倍楽観的だと分かりました。** 見込み +0.0041 に対し実測 +0.0018（達成率44%）。しかも **ongoing 側の改善は転移するが、onset 側の改善は転移しない**という規則性が3回の提出で確認できました（第7章）。

## 3. R で変えたこと

### 3.1 構成

| 部分 | M | R |
|---|---|---|
| Task 2 onset | 0.7 × LightGBM ＋ 0.3 × CNN（3本平均）、IoU 期待値最大化で判定 | **変更なし** |
| Task 2 ongoing | 0.5 × LightGBM ＋ 0.5 × CNN（3本平均）、しきい値 0.60 | **0.25 × 全体状態LightGBM ＋ 0.50 × Transformer（4本平均）＋ 0.25 × CNN（3本平均）、しきい値 0.45** |
| Task 1・3・4 | ― | **変更なし** |

Transformer は 9/15 に「3つ目のモデル系統」として学習したもの（GRU ＋ パネル全体の注意機構）で、シード s3〜s6 の4本です。**すでに測定済みで、候補Oとして構築したまま提出していなかったもの**です。

### 3.2 重みの決め方（貪欲法＋交差検証）

手で決めた 0.5/0.5 をやめ、キャッシュ済みの全モデル系統11種から貪欲法（同じモデルを複数回選べる方式）で重みを選びました。**片方の月で重みを決め、もう片方の月で評価**する交差検証を両方向で実施しています。

| | validation で決めて private で評価 | private で決めて validation で評価 |
|---|---|---|
| M 本番（しきい値0.60） | 0.8154 | 0.8207 |
| しきい値 0.50 にするだけ | +0.0093 | +0.0118 |
| 候補O（0.5×全体状態LGBM ＋ 0.5×Transformer3本） | +0.0219 | +0.0192 |
| **貪欲法で選んだ重み** | **+0.0329** | **+0.0294** |

両方向で **Transformer のシード群が最大の重み**を取り、**本番の LightGBM は一度も選ばれませんでした**。その情報は全体状態 LightGBM と神経系モデルで代替できているためです。

最終的には、両方向で共通して選ばれた3系統を丸めた重み **2:1:1**（Transformer : CNN : 全体状態LightGBM）を採用しました。6系統の細かい重みは窓のノイズに合わせにいく危険があるためです。両月で確認した結果が下表です（family mean は公式スコアが使う集計）。

| | validation | private |
|---|---|---|
| M 本番 | 0.8057 | 0.7928 |
| **R（2:1:1、しきい値0.45）** | **0.8327** | **0.8216** |

### 3.4 提出前の検証（3点とも通過）

1. 変更された窓は **ongoing のみ**（validation 32窓・private 34窓、いずれも全40 ongoing 窓の内数）。**onset 窓はゼロ**で、スクリプト改修が onset 経路に影響していないことを確認。
2. queue ファイルの行キー（window_id・timestamp・link_id）は M と完全一致。
3. 提出物全体 6,980,503 行を突き合わせ、**差分715行はすべて task=queue**。速度・流量・経路交通量は1行も変わっていない。

## 4. ongoing の誤り構造（今回はじめて分解しました）

これまで onset ばかり分析しており、S_queue の半分を占める ongoing は未分解でした。分解した結果：

- 誤りの **70% は「渋滞を見落とした側」**。過剰予測ではない。
- T時点で見えている渋滞を基準に分類すると、**最大の塊は「伸び」（これから渋滞が届くセル）で全誤りの42〜47%**、そのクラス内の誤り率は33〜40%。「解消」が17〜18%、「持続」は4%でほぼ解けている。
- 地平線別では **T+25・T+30 の2ステップだけで損失の43〜45%**。
- 永続予測（T時点の渋滞を固定）は 0.666、M は 0.821。

**つまり ongoing は「渋滞がどこにあるか」ではなく「渋滞の端がどれだけ伸び、どれだけ捌けるか」の問題**でした。

## 5. 伸びなかったこと（今回分、すべて測定済み）

| 試したこと | 結果 |
|---|---|
| **衝撃波の物理特徴**（渋滞端の実測移動速度＋Rankine–Hugoniot 速度を地平線ごとに投影） | 単体では明確に有効（ongoing +0.018〜+0.020、M のブレンド内でも +0.007〜+0.008、伸びの誤り率 0.30→0.26）。**しかし新アンサンブル内では上積みゼロ、private では −0.0032 で悪化**。Transformer が同じ情報を既に捉えており冗長。**不採用** |
| onset のアンサンブル（重み最適化） | 交差検証で **−0.021／0.000**。onset は1スプリット169窓しかなく重み選択が過学習する。M の 0.7/0.3 を維持 |
| ongoing のセル単位しきい値（地平線×渋滞内外×端からの距離の60群） | 大域しきい値0.50に対し**上積みゼロ**。伸びの取り逃しはしきい値の問題ではなく確率の問題 |
| 窓ごとしきい値の学習（ゲート） | 交差検証で +0.014〜+0.018。オラクル（+0.080）の2割しか取れず、アンサンブル（+0.029）に内包されるため不採用 |
| リンクの向き補正（S/W パネルは下流→上流順） | 余裕度・構造特徴を正しい向きで作り直しても改善なし。**正しい向きがブレンド内で最も悪い**。向きの効果はパネル横断学習のノイズ（0.01〜0.05）に埋もれる |
| Task 1 のテスト時学習の延長 | 400→1200ステップで総合 +0.0010→+0.0013、**3600ステップでも +0.0013 で飽和**。現行（400ステップ）からの上積みは +0.0003 で、月ごとの再学習・10パネル推論・行差し替えの手間に見合わず見送り |

## 6. どこまで行けるかの上限（オラクル測定）

推測を避けるため、「神の目で正解を与えたら最大いくらか」を測りました。

**onset 側**
- 真のボトルネックを100%当て、trainのテンプレートで形を描く → onset IoU 0.93。**それでも総合は 0.897 止まり**。
- 外した窓（12%）の分析：外す窓ほど候補間のスコア差が**大きい**（自信満々に間違えている）。真のボトルネックは中央値26リンク離れた「その run では珍しい場所」で、モデルは「いつもの場所」を予測している。
- LightGBM と CNN の不一致は誤りの1/20しか含まず、振り分けの手がかりにならない。

**ongoing 側**（総合換算＝ 0.15 × ongoing の増分）

| 完璧に直す対象 | 総合換算 |
|---|---|
| 伸び | +0.008 |
| 解消 | +0.007 |
| 渋滞端から±1リンク以内の全セル | +0.011 |
| ongoing を完全に当てる | **+0.025** |

決定側（しきい値・ゲート）は使い切り、手作り特徴は Transformer に吸収され、onset は情報限界にあります。**+0.01 を1つの施策で得る道は残っていません。**

## 7. 局所評価の較正（今後の運用に直結します）

3回の提出で規則性が出ました。

| 変更 | 局所の見込み | LB 実測 | 達成率 |
|---|---|---|---|
| L → M（CNN ブレンド、ongoing 主体） | +0.008 | +0.0061 | 0.76 |
| M → Q（渋滞地図、onset 側） | +0.002 相当 | −0.0016 | 負 |
| M → R（ongoing アンサンブル） | +0.0041 | +0.0018 | 0.44 |

原因ははっきりしています。**公開LBは1パネルあたり onset 5窓・ongoing 5窓しか採点しません**（validation で ongoing 40窓）。一方われわれの評価は公式に近い窓3,351個を使っており、84倍の標本です。窓あたりのセル数も onset は1〜5、ongoing は数百です。

**運用規則（以後これに従います）**
1. 局所の見込みは**半分に割り引いて**から提出価値を判断する
2. 対応ありブートストラップの信頼区間が**両月とも**0を跨がないことを条件にする
3. **onset 側の改善は数値の大小によらず未証明として扱う**（渋滞地図・onset アンサンブルの2回失敗）
